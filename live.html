What this is

An algorithm is a function that takes inputs and returns a set of open orders. This page documents one that runs by itself every night. A GitHub Action wakes up at 10pm ET, reads the latest AMZN prices and my current book, pulls this week's AMZN option chain from LSEG, decides what the wheel should do next, and commits the answer as open_orders.json in the root of this repo. Sanji, the course server, reads that file, resolves it against the next session's prices, and writes back the new book. The next night the function runs again on the new book. That is the loop.

The strategy is the wheel I backtested on AMZN: sell a 30-delta put each week while holding cash; if it is assigned, sell a 30-delta covered call each week until the shares are called away; then start over. The live version uses exactly the rules and parameters of that backtest, so the evidence on the backtest page is evidence for what is running here.

The loop

Two workflows do the work, both modeled on the class examples. nightly.yml runs on the cron 0 3 * * * (03:00 UTC is 10pm EST and 11pm EDT), installs Python, runs the script with my LSEG credentials from GitHub secrets, and commits only the files the algorithm owns. pages.yml redeploys this site when the nightly finishes. Sanji owns price_history.json and the positions file; the Action never touches them.

The algorithm

Book (read from positions.json)Next session is the first of its week?Order writtenWhy
Cash onlyYesSell 1 AMZN put, this week's expiry, strike nearest 30-delta, limit orderStart a wheel cycle: get paid to commit to buying 100 shares below the market

AnythingNoNothingThe backtest only opened options on the week's first session (Monday, or Tuesday after a Monday holiday)

Assignment is not an order. Sanji applies it from the closing price: a short put that closes in the money becomes 100 shares, and a short call that closes in the money takes them away. The algorithm only has to read the book Sanji wrote and act on it. Until Sanji starts publishing positions, the script treats the book as cash, so every Monday it plans a fresh put.

Choosing the strike

  

    
Sanji's order language has a delta:30 strike token, but Sanji rejects it until the course
       database stores option chain snapshots, and it rejects mid limit prices for the same reason.
       So the script does that work itself and writes a fully named contract: an exact expiry date, a plain strike
       number and a plain limit price. Sanji then only needs that contract's daily bar to resolve it.

    
    
      
  1. Find this week's expiry. LSEG discovery search lists the AMZN options expiring in the week of the
          next session; the script takes the last one in that week (normally Friday; Thursday when Friday is a holiday).
    2. 
      
  2. Get last night's quotes. Bid and ask at the prior close for out-of-the-money puts (85% to 102% of spot)
          and calls (98% to 115%). Mid = (bid + ask) / 2, the same fill assumption as the backtest.
    3. 
      
  3. Back out implied volatility. Solve Black-Scholes for the vol that reproduces the mid, with time measured
          from the quote date: Tquote = (expiry − quote date) / 365,
          r = 3.75%, no dividend.
    4. 
      
  4. Re-value at the order session. With that vol and the last close as spot, compute delta and a model
          price with Ttrade = (expiry − order date) / 365. This is how the backtest
          measured delta (on the entry day), and it removes the weekend's time decay that a Friday quote still contains.
    5. 
      
  5. Pick and price. The out-of-the-money strike whose |delta| is closest to 0.30 (ties go further out of the
          money, Sanji's own tie rule). The limit is that model price rounded down to the cent.
    6. 
    

    
The limit works as a floor, not a target. Under Sanji's rules a sell limit fills at the open whenever the open is
       already at or above the limit, so on a normal Monday the put is sold at its opening price. The limit only stops a
       sale when the option opens far below what last night's chain implied.

Why this strategy

  

    
Why the wheel. It is the options strategy that most needs the loop. Every decision depends on the book:
       whether we hold cash, shares, or an open option. A strategy that ignores positions would just print a signal;
       this one reads what Sanji says happened and reacts, including to assignment, which only the server can apply.

    
Why AMZN and 30-delta weekly. Because that is what I backtested from January 2024 to October 2026 with
       LSEG option data, so the parameters were fixed before this live version existed. Sanji seeded this repo with
       AAPL at random; I added AMZN's conid to price_history.json so Sanji tracks it too.

    
What the backtest says, honestly. The wheel delivered lower risk, not higher return. It trailed both AMZN
       buy-and-hold and SPY on return and on Sharpe, but with lower volatility (13% against 18%) and a smaller maximum
       drawdown (-13% against -18%). It behaves like a smaller, smoother AMZN. The point of this assignment is the machinery, and the backtest is what keeps the
       live rules honest.

Built for Sanji

  
    
    
  • The right session date. for is the first NYSE session strictly after the run date, from
        exchange_calendars. Friday night plans Monday; the night before Thanksgiving plans the half-day
        Friday. A manual run during market hours never plans a session that has already opened.
    • 
    
  • Safe to rerun. Order ids are built from the session date (amzn-csp-2026-11-23), so the
        Saturday and Sunday runs rewrite the same order instead of adding new ones. Old orders stay in the file:
        Sanji ignores ids it already filled and dates already past, so keeping them costs nothing and means a
        late-resolving order is never deleted.
    • 
    
  • Validated before it is written. Every order is checked against the spec on the order page: allowed
        fields, required fields, expiry and strike tokens, market versus limit rules, unique ids, and that the session
        is a real NYSE trading day. It also enforces two wheel rules: never buy back or sell what the book does not
        hold, and never sell a call that is not covered by shares.
    • 
    
  • Fails loudly. If LSEG is unreachable, quotes are missing, or the positions file has a shape the script
        cannot read, the run stops with a red X in GitHub and writes nothing. A stale or misread book is worse than a
        skipped night.
    • 
    
  • Both file locations. The assignment asks for open_orders.json at the repo root; the order
        page says Sanji reads mkt/open_orders.json. The script writes the same file to both.
    • 
    
  • Fresh deploys. The class Pages workflow checks out workflow_run.head_sha, which is the
        commit the nightly started from, not the one it pushed. This repo checks out the latest commit instead, so the
        site shows tonight's orders and not last night's.
    • 
  


  
Limitations

  
    
    
  • Sanji does not resolve orders yet. Until it does, there are no fills, no positions file and no live
        P&L. The algorithm is written for the book it will receive; the positions parser stops rather than guesses
        if the real format differs from what it expects.
    • 
    
  • Strikes come from last night's close. If AMZN gaps over the weekend, Monday's "30-delta" strike can
        be well away from 30 delta at the open. Sanji's delta:30 token measured at the open would fix this once it is enabled.
    • 
    
  • The limit is a loose floor. Measuring time in calendar days counts the whole weekend as decay, so the
        model price sits well below Friday's mid. That makes fills likely, matching the backtest, which never skipped a week,
        but it only protects against an option that opens far too cheap.
    • 
    
  • No buying-power check. Sanji does not check cash, and neither does the script; it always sells one put,
        which needs about 100 times the strike in cash.
    • 
    
  • Same weaknesses as the backtest. Capped upside in rallies and full downside below the strike. The
        backtest shows the cost: lower return than simply holding AMZN.
